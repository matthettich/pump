# Developing …pump

**Picking this up? Read [HANDOVER.md](HANDOVER.md) first**: current state, what is verified, and the open items
(the NAM memory-safety finding is fixed: patches/nam/).

Mastering plugins and creative effects by wake, built on DPF (VST3 + CLAP everywhere, AU on macOS). Every plugin
shares one DSP library, one UI kit and one look: Thunder Plus's **Simple** skins (flat, square, 1.5 px ink outlines, offset blocks behind
keys and screens, Share Tech Mono labels) in one light-neon accent per plugin, light or dark.

## Conventions

- Parameter **symbols never change** once released (sessions and presets store them).
- Parameters are **append-only**: VST3 parameter ids are DPF's indices, so inserting or removing one shifts every
  later id and breaks automation in saved sessions. An unused parameter stays as a hidden placeholder (the EQ's
  `audition*` parameters are).
- Listening and display state (solo, audition, analyzer mode) is flagged `kPNoUndo`: it isn't part of undo, A/B or
  presets. Things that only last while a key or mouse button is held (Alt-hold solo/audition) don't go through
  parameters at all: the UI sets atomics on the plugin (direct access), so they're never saved or echoed by hosts.
- Nothing that allocates, locks, joins threads or builds kernels runs on the audio thread. The EQ's linear-phase
  convolver is built on its worker thread and swapped in at a block boundary (see `Engine::pollLinear`); old objects
  are handed back to the worker to be freed.
- The command modifier is `cmdKey(mod)`: Cmd on macOS (where Ctrl-click means right-click, mapped in `onMouse`),
  Ctrl elsewhere.
- Parameters are atomics on the plugin; `run()` calls `takeAnyChanged()` / `takeChanged(i)` and pushes changes to the
  engine at block start. No allocation, locks or file access on the audio thread.
- Report latency with `setLatency()` (from `run()` when it changes) and keep the bypass path latency-matched
  (`BypassMixer`). Dry/wet mixes must line up sample-exactly.
- Wrap `run()` in `pump::DenormalGuard`.
- UI reads meters/analyzers through `getPluginInstancePointer()` (DISTRHO_PLUGIN_WANT_DIRECT_ACCESS): the plugin
  exposes `pump::ScopeRing`s (sample feeds) and `pump::MeterValue`s (max/min-hold values the UI `exchange()`s).
- UI coordinates are logical (the window scales uniformly). Header is 46 px, footer (status line) 24 px.
- Look: use `theme.*` colours only. `keyBox()` for keys, `screenBox()` for graph areas, `caption()` for small-caps
  section labels, `kLabel` font for words, `kMono`/`kBold` for numbers. Neon = highlight fills/curves; ink = text,
  outlines, filled "on" keys; `second` = a contrasting curve (side channel, gain reduction).
- Controls: `addDial` (flat dial), `addRow` (Simple slider row), `addToggle`, `addButton`,
  `addSegmented`, `addMenu`. The interaction rules are built in: drag (Shift fine), right-click to type,
  double-click or Ctrl/Cmd/Alt-click resets, wheel steps. Override `formatParam()` for plugin-specific value text ("OFF" at
  a filter's end stop, note names); controls and the status line use it.
- Tempo-synced effects set `DISTRHO_PLUGIN_WANT_TIMEPOS 1` and read `transport()` at the top of `run()`. Engines
  only see `pump::Transport`, lock to the song position when the host plays and free-run at the host tempo when it
  doesn't (120 BPM when the host sends none).
- Every plugin has: factory presets (first one "Default"), A/B, light/dark, bypass, a status line, resizing.
- Momentary controls (Alt-listen, band listen, meter reset) are `kPHidden` parameters: hidden from hosts and never
  stored in undo or A/B snapshots.
- Parameters that change latency or topology (lookahead, oversampling, FFT size, band count, crossover type) are not
  automatable; changing them fades out, switches, and fades back in.
- **Parameters are only ever added at the end.** Hosts save parameter values and automation by index (the VST3 and
  CLAP ids are the index), so inserting one, reordering or removing one remaps every saved session. A parameter that
  is no longer used stays as a hidden placeholder (`kPHidden`). `make tests` checks this against
  `tests/data/param_ids.txt`; after adding parameters at the end, run `PUMP_WRITE_PARAM_IDS=1 ./build/tests/test_presets`
  and commit the file. If a saved value ever has to change meaning, bump `kPumpSessionVersion` (common/PumpPlugin.hpp)
  and migrate on `sessionVersion()`.
- Real-time rules: nothing on the audio thread allocates, frees, locks or throws. Objects loaded off the audio thread
  (sounds, wavetables, voicebanks) go through `pump::Retained` (common/dsp/Retained.hpp); kernels and lists that the
  audio thread swaps in use an atomic pointer and give the old one back on an `SpscPtrQueue` (common/dsp/Util.hpp).
- `setState()` runs in the host's session load: a file loader there catches everything (an exception escaping it
  takes the host down). File names are UTF-8: open and list files through common/FilePath.hpp, never with a plain
  `fopen` / `std::ifstream(std::string)` (they read the ANSI code page on Windows).

## Build and test locally

```
export PKG_CONFIG_PATH=/home/claude/sysroot/pkgconfig        # local GL headers for the Linux UI build
make -C plugins/eq DPF_PATH=/home/claude/dpf jack vst3 clap  # /home/claude/dpf = DPF + a headless test audio backend
make -j8        # every plugin (the shared DPF graphics library is built once first)
make tests                # DSP tests (also runs the licence-boundary check)
make tests-asan           # the self-contained tests under ASan+UBSan
make tests-tsan           # and under ThreadSanitizer (slow: heat takes several minutes)
DISPLAY_NUM=:101 tools/shot.sh bin/pump-eq /tmp/eq.png 1 0 4  # preset 1, light, after 4 s of the test mix
```

Only the standalone (`jack`) builds read the `PUMP_TEST_*` variables (through `pump::testEnv`; `make jack` builds them
with `PUMP_TEST_HOOKS=1` in a build folder of their own), so the released plugins never do. The standalone build runs headless with `PUMP_TEST_AUDIO=tests/data/mix.f32` (made by tools/make_mix.py; 8 bars of drums,
bass, pads and a lead with two deliberate resonances, peaking at -6 dBFS). `PUMP_TEST_PRESET=<n>` loads a factory
preset at startup and `PUMP_TEST_DARK=1` starts dark — both only matter for screenshots.

`make` applies the DPF patches first (also when a plugin is built directly with `make -C plugins/eq`); with a DPF
that isn't a git checkout (DPF_PATH=...) it uses patch(1).

CI (`.github/workflows/build.yml`) cross-compiles Windows x64 with MinGW (posix threads), builds macOS universal,
builds Linux, runs `make tests` and the sanitizer runs (`tests-asan`, `tests-tsan`), and refreshes the `latest` pre-release on every push to main.

## WebAssembly (Thunder Plus's bus and master effects)

`wasm/pump_wasm.cpp` puts the nine engines behind one C interface (`pump_new(type, sr)`, `pump_values` /
`pump_commit`, `pump_process`, `pump_tel` for the meters, `pump_ring_*` for the UI feeds, `pump_hold` for Alt-listen;
the list is at the top of the file). Each `Host<Name>` there is its plugin's DSP side with the DPF parts taken out:
the same prepare / activate / sync / run code, chunk sizes, `BypassMixer`, sanitising, `ScopeRing`s and `MeterValue`s.
`HostBase` stands in for `PumpPlugin` (values with change flags, `pv`, `takeAnyChanged`, `takeChanged`).
**When a `Plugin<Name>.hpp` changes, change its `Host<Name>` the same way**, and rebuild.
Handles from `pump_new` / `psyn_new` are opaque (slot and generation, wasm/Handles.hpp): JavaScript must not treat
them as small array indices, and a handle used after `pump_free` is ignored. Staged values that aren't written before
`pump_new` take the parameter's default.

```
WASI_SDK=/path/to/wasi-sdk-25.0-x86_64-linux make wasm     # = sh wasm/build.sh: build/wasm/pump.wasm, build/wasm/pump-meta.js
c++ -O3 -ffast-math -fno-finite-math-only -std=c++17 -DPUMP_SYNC_KERNELS=1 -DPFFFT_STATIC_DEFINE -Icommon \
    wasm/compare.cpp -x c common/pump_pffft.c -o build/pump_compare
node wasm/compare.mjs build/wasm tests/data/mix.f32 10    # wasm vs native: difference, latency, CPU per effect and preset
```

Thunder Plus vendors `pump.wasm` and `pump-meta.js` in its `pump/` folder (bump their `?v=` there); its
`docs/PUMP-FX.md` describes how it uses them. `pump-meta.js` is generated from the Params.hpp tables, so its parameter
ranges and factory presets always match the plugins.

**The instruments** (`wasm/pump_synth.cpp`, built into `pump-synth.wasm` with `pump-synth-meta.js`): MONO, POLY and
COIL behind `psyn_new(type, sr)`, `psyn_values` / `psyn_commit`, `psyn_midi(h, frame, status, d1, d2)` (queued for the
next call, at that sample) and `psyn_process(h, n)` into `psyn_out(0/1)`; `psyn_latency` is MONO's oversampler. Each
`Synth<Name>` is its `Plugin<Name>.hpp` without DPF: the same `sync()` from the values to the engine's `Settings` and
the same 256-sample chunks with the MIDI in each (no on-screen keyboard, no COIL KICK key). **When a `Plugin<Name>.hpp`'s
`sync()` or `run()` changes, change its `Synth<Name>` the same way.** Thunder Plus vendors both files in `pump/synth/`
(`pump-synth-engine.js` there renders a pad's note with them); to add an instrument, add a `Synth<Name>`, its `Type`, a
`dump()` line in `pump_meta.cpp`'s `synth` mode, and its entry in that glue file.

An AudioWorklet has no threads, so the wasm build sets **`PUMP_SYNC_KERNELS=1`** (`common/dsp/Util.hpp`): the kernels
the plugins design on a worker thread are designed on the calling thread instead, at the point the worker would have
picked the request up (`Multiband::Splitter::designRequested`, the EQ's `pollLinear` / `requestKernel`; the EQ builds
at most one linear-phase kernel every 80 ms of audio while settings move). No `std::thread`, mutex or atomic
`shared_ptr` is used then. The plugins never set it; `make tests` also runs the EQ, BAND, WIDE and HEAT tests built
that way (`build/tests/sync_test_*`) and the wrapper test.
